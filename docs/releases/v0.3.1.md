## What you get

0.3.0's village with the fixes from your test:

- **The river.** The photo's own colour (× 0.9 instead of × 0.6), less of a mirror (roughness 0.3 instead
  of 0.05), smaller, stronger ripples drifting apart at 0.8 m/s with no net direction (0.3.0's drifted
  slowly downstream), and the bank fading over 1 m instead of a 0.2 m edge.
- **The frame rate.** At most 60 frames a second, at most 15 while the pause screen is open.
- **The edges.** 4× MSAA on the 3D view.
- **The log.** Every line is written to `godot.log` and the console when it is printed, so the log fills
  while the game runs.
- **A missing data pack is named.** The log and the red error panel name the missing pack, what it holds
  and the folder it is missing from, and every message about a missing or damaged file in a release says
  to download the release folder again instead of naming a pipeline command. `tools/export.sh` now refuses
  to build a release whose packs are not exactly the ones the game expects.

Everything else is 0.3.0's: the controls, the start view, the light (exposure 0.54, your 1b), the credits.

## What the review found

Each batch was built by a builder agent on Sonnet in its own worktree (its pinned tests red first, then
green, its mutation rows run) and reviewed by one reviewer on this session's model: no P0, P1 or P2 in any of
the six. The whole-range review (three lenses over every change since the plan, and the seams between
batches, every serious finding re-checked by a skeptic; `docs/reviews/v0.3.1-round1.md`) found no P0, P1 or
P2 either: the one P2 raised was graded P3 by its skeptic. In plain words, the P3s:

- the river's second ripple pattern will jump once an hour of play, when Godot's clock wraps (a next-release
  fix);
- two comments in the render check claim a little more than it checks, and two copies of "where the packs
  are" live in two scripts;
- the export's test stand-in packs an empty folder where the real pack tool refuses, and a refused export
  can leave an unfinished `build/` folder (never copied to `dist`);
- the M4 plan's note now tells the next release which of M4-10's older pins to rebuild on 0.3.1's.

All are on the board. Two process slips, recorded in the ledger: batch 5's builder ran its commit's gate
through a pipe instead of chaining the commit to it (the gate had passed, and its batch gate passed again from
a clean worktree), and a container restart lost the first run of batch 4 four minutes in, before any code
(it was re-run from the same commit).

## What 0.3.1 does NOT prove: please look at these

1. **That it renders and looks right on your GPU**, and above all **that it starts at all with 4× MSAA.**
   Software Forward+ crashed on the real village with 4× MSAA during the planning (the software Compatibility
   renderer drew it). If the game closes or shows nothing, put a file `override.cfg` beside the executable
   with the two lines `[rendering]` and `anti_aliasing/quality/msaa_3d=0` (the README says so); 0.3.0 in
   `mattini-0.3.0/` is the rollback.
2. **The river,** close and from 30 m, and looking towards the sun: the colour, the ripples (do they read as
   moving?), the bank; whether the near-black patch is gone.
3. **The GPU** at 60 fps and at 15 paused, against 0.3.0's 94 %: heat and fan. To see the frame rate, start
   the game from a terminal with `--print-fps`. If the load is still high, the river's shader is the first
   suspect (it reads the class grid 36 times per pixel, never measured on a GPU).
4. **The log** filling while the game runs (Linux: `~/.local/share/godot/app_userdata/mattini/logs/godot.log`).
5. **The edges** of trees and buildings with 4× MSAA.
6. **The credits scroll** at 15 fps while the pause screen is open: choppier than before, by design.
7. **The Windows build,** never started anywhere (deferred by you).
