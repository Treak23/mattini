## Goal

`python -m mattini shadows` builds the capture shadows mask (brief v0.5.0-01's `build_shadows`)
from the downloaded swissSURFACE3D tiles, as `trees` builds the trees, then writes the manifest
and prints its path. The manifest gains one key, `shadows` (eleven keys at the top): the
description `shadows/<area>.json`, checked world, then the lock's fit, then the inputs, then the
block, or null until the step has run in the folder. The seven M2/M3 fixture manifests gain one
line, `"shadows": null`, and the shadows fixture gains a manifest of its own. Nothing in the game
changes (the reader and the lift are later batches of lane G).

Production code is `main` after v0.5.0-01 has landed (`pipeline/mattini/shadows.py`). The pin
author rehearsed this brief in a clone of `d522abf` with v0.5.0-01's pins and throwaway
`shadows.py` committed on it (2026-10-30): the pins red on that code, green on a throwaway
implementation, the full gate, all sixteen mutation rows both ways, and the real run on the six
real tiles from the command line. Every number marked "rehearsal" was measured there. The pin
author's record is `docs/briefs/sketches/v0.5.0/v0.5.0-02-PINSPEC.md`, committed by the session;
you do not need it.

1. **The command** (M4-09 decision 1, the shadows only). `python -m mattini shadows` takes `--raw`
   (default `data/raw`) and `--out` (default `game/assets/generated`), "as `trees` does", with the
   same help texts as the other steps' options. It loads `config/world.json`, `datasets.json`,
   `datasets.lock.json` and its own config through the module, calls the step through the module,
   then writes the manifest and prints its path on stdout (progress on stderr):
   ```python
   shadows.build_shadows(world, datasets, pinned, shadows.load_shadows_config(), raw_root, out_dir, progress=progress)
   return write_manifest(out_dir)
   ```
   - `shadows` joins `from mattini import …` in `__main__.py`; the tests replace
     `shadows.build_shadows` on the module (a name imported into `__main__` would not be replaced).
   - Its sub-parser comes after `trees` and before `sky`, so the help lists, in pipeline order:
     `lock, download, terrain, buildings, photo, roofs, surfaces, trees, shadows, sky, manifest`
     (M4-09's order without `surroundings`). The rehearsal added `"shadows"` as the last entry of
     `STEPS` and one branch to `_build_step`; any placement that keeps the order and the behaviour
     is yours.
   - The dispatch sits inside `main()`'s `try`, so a Ctrl-C is M3-03's one handler (one line
     naming `python -m mattini shadows`, exit 130), and `shadows.ShadowsError` joins the `except`
     tuple: one `mattini: error: …` line, exit 1, no traceback.
   - Without the download, the step's own refusal (v0.5.0-01 Decision 4) names
     `python -m mattini download surface` and writes nothing, not even the output folder (M4-09
     decision 9: "`shadows` before `download surface` names `download surface`").
   - The module docstring of `__main__.py` says what `shadows` does.
2. **The manifest** (M4-09 decision 3, the shadows only; the session's decision: eleven keys, no
   `surroundings` key until the far mountains' step exists). In `manifest.py`:
   - `build_manifest` and `write_manifest` gain the keyword
     `shadows_config_path=SHADOWS_CONFIG_PATH` beside the others; `write_manifest` passes it
     through.
   - `shadows_config = load_shadows_config(shadows_config_path)` is loaded with the other configs,
     always ("every step config is loaded and checked even when its step has not run"): a shadows
     config the loader refuses is refused with nothing built.
   - `"shadows": <the block>` in the returned dict, so the top level is exactly `buildings, photo,
     roofs, schema, shadows, sky, surfaces, terrain, trees, world, world_sha256`; schema stays 1;
     serialised and written as today (sorted, indent 2, LF, through `manifest.json.part`).
   - The block is the description `shadows/<area>.json` for config/shadows.json's one area
     (`terrain.configured_area(shadows_config)`), verbatim, as `shadows.built_shadows_block`
     returns it; null when that file is absent (M3-13's rule; the gate's `manifest` step writes
     `"shadows": null`). Never `{}`, never left out.
   - The module docstring's "Its top level is exactly …" sentence names the eleven keys, and its
     list of blocks says where the shadows block comes from.
3. **The check order for a built `shadows` block, in `manifest.py`** (M4-09 decision 4, the
   shadows only, quoted: "M3-13's `_Step`, uniform"):
   1. `computed_for.world_sha256` against the world (design's step, naming config/shadows.json);
   2. the lock's fit through `lock.fit_problem` for `swisssurface3d`, naming
      `python -m mattini lock surface` and no other command;
   3. `computed_for.inputs_sha256` against `lock.entry_sha256` of that entry (design's step);
   4. the step's `built_shadows_block`.

   Refusals use the step's error class (`ShadowsError`), pinned directly: `build_manifest` itself
   raises a `ShadowsError` for a lock that does not fit, other inputs and a changed world (the
   release's checkers, 2026-10-30: through `cli.main` another step's class, the trees', would pass
   unseen, since the `except` tuple holds every step's). The manifest makes checks 1 to 3 itself,
   whatever `built_shadows_block` checks (the module docstring's "in the same order whatever the
   steps' block functions check"): the pins replace `built_shadows_block` by a stand-in that
   refuses everything, and the first three refusals must still be the manifest's (pin author;
   the stand-in is set on both `mattini.shadows` and `mattini.manifest`, so either import style
   is caught). The rehearsal did it in one line beside the other steps':
   `_SHADOWS = _Step("shadows", SHADOWS_CONFIG_NAME, (SURFACE,), ShadowsError)` and the same
   `checked(...)` pattern as the surfaces' block.
