# RELEASE.md — what must be true before a build reaches the owner or anyone else

Walk it top to bottom before any version bump.

## A. Preconditions — every one, or the release stays unpublished

- [ ] `git status --porcelain` is empty.
- [ ] Every brief in the release reads `Status: DONE (<sha from origin/main>)`.
- [ ] No production code in the release was written by the session's own hand (DESIGN.md
      §Identity, lesson 15).
- [ ] No truncated review round (a dead agent, a limit hit); a truncated round is a round
      that did not happen, and the whole-range review ran (DESIGN.md §The release step 4).
- [ ] No batch was started past 100 % of the go's budget (WORKFLOW §The release has a size);
      the batches not built are on the next release's list.
- [ ] No gate is a source census standing alone over code that runs at scene load,
      `_ready()`, autoload initialisation or pipeline start-up (BUILD.md card 8).
- [ ] Every gate's "does NOT prove:" line is filled in. Read them as a set: they are the
      honest list of what this release has not been shown to do, and the report-back
      names the visual ones for the owner to look at.
- [ ] **Attribution:** the credits show `© swisstopo` and any dataset-specific wording
      for every dataset in the build (CLAUDE.md Hard Rule 3), and the licence notices of
      the third-party code the build ships: Godot and its components, Terrain3D, and
      godot-cpp, which is compiled into Terrain3D's library (all MIT; its notice since
      M2-02, `game/credits/godot-cpp-LICENSE.txt`; 0.1.0 lacked it, D17). From 0.4.0 the
      stars' credit, word for word as `game/sky/stars.csv`'s first line ("Stars derived from the
      Hipparcos Catalogue … Credit: ESA. CC BY-NC 3.0 IGO" with the licence's URL), on the pause
      screen and, from 0.5.0, in the Release notes (`tools/release_notes.md`; up to 0.3.1 the
      `dist` README): CC BY-NC 3.0 IGO ends on a breach (SPEC §13 row 51). The notes carry the
      pause screen's Sky credits (the sun's and the moon's sources) word for word too, and
      name the software that ships, not GUT (brief v0.5.0-15 ties them to `main.gd` by a test).
- [ ] **No raw data or unmanaged binaries** entered git history in this release, but the
      one real sample the owner allowed (SPEC §13 row 24), which `test_repo_hygiene.py`
      names with its SHA-256.

## B. The bump

- [ ] Version raised in `game/project.godot` (`application/config/version`) and shown
      in the game on the pause screen, the only place it shows (SPEC §11, §13 row 15).
- [ ] Full gate from clean, redirected to a log, exit status checked; never piped.

## C. Delivery — GitHub Releases, the owner's "1a" (2026-10-29; SPEC §11, §13 row 54)

From 0.5.0 a release reaches the owner as a **draft GitHub Release** that
`.github/workflows/release.yml` builds on a GitHub-hosted runner from the pinned inputs and the
owner publishes. The `dist` branch stays as it is, the record of 0.1.0 to 0.3.1 under its named
folders (`mattini-0.3.1/` and the two before it) with its own README; nothing is pushed to it any
more. The container's release gate below is the session's proof; the workflow repeats the same
build on GitHub's machine, and its log is the delivery's proof.

**The session's proof, in a container** (DESIGN.md step 5; a fresh clone, solo):
- [ ] The generated assets the build ships were regenerated by the pipeline from the
      pinned inputs (SPEC §Storage) in the fresh clone, not copied from an unknown one, in this
      order: `terrain`, `buildings`, `photo`, `roofs`, `surfaces`, `trees`, `shadows`, `sky`,
      then `manifest` (the workflow's order, pinned by `pipeline/tests/test_release_workflow.py`).
- [ ] Every built output has its designed value: the village heights at 0.5 m `b6334c1f…`
      (SPEC §8); the six building chunks (`config/buildings.json`); from M3, the photo's
      pixels and JPEG (`config/photo.json`), the roof colours (`config/roofs.json`), the
      surfaces by their pixels and their PNG's bytes (`config/surfaces.json`: the PNG's
      bytes depend on the zlib build, so they are design's too; a machine whose zlib writes
      other bytes is refused, M3-R1-fix-6), from 0.4.0 the river's flow grid by its pixels and
      its PNG's bytes (`config/surfaces.json`: `c05a7535…`, `c51120dd…`), the six tree chunks
      (`config/trees.json`), from 0.4.0 the sky's site (`config/sky.json`) and from 0.5.0 the
      capture-shadow mask by its pixels and its PNG's bytes (`config/shadows.json`: `203cae73…`,
      `918dfdf6…`, the surfaces' zlib rule). Every step compares before it writes, and
      `manifest` refuses any other file (M2-01, M2-04, M3-04 to M3-07, M3-13, v0.5.0-01, -02),
      so their exit 0 in the fresh clone is the check.
- [ ] The fresh clone's `game/assets/generated/manifest.json` has the size and SHA-256
      the release's plan names (0.5.0: 326'124 bytes,
      `f68275a1c292f3933944db7daa5231fdad7e42fa16b263b0611a81af857029fe`, 0.4.0's with the
      shadows block; 0.4.0: 324'931 bytes, `a03c5722…`; 0.3.1: 324'359 bytes, `3ca0445c…`),
      compared by a command, its output in the release record:
      `test "$(wc -c < game/assets/generated/manifest.json)" -eq 326124 && echo "f68275a1c292f3933944db7daa5231fdad7e42fa16b263b0611a81af857029fe  game/assets/generated/manifest.json" | sha256sum -c -`
      (each release's plan names its pair: the last release's when no batch changes a
      generated file, else the pair measured at the go). The same pair goes into the workflow's
      inputs below.
- [ ] Windows and Linux exports built by `tools/export.sh` with the pinned Godot version's
      export templates, each with its data packs beside the executable (steps 4–4b:
      `mattini-terrain.pck`, `mattini-photo.pck`; from M3-08, SPEC §11); its log carries "the
      game expects mattini-photo.pck mattini-terrain.pck, as written here" (step 2b, from
      0.3.1), quoted in the record.
- [ ] Every generated file ships once, byte for byte: `tools/export.sh` step 4c reads the
      directory of every pack in both folders and compares it with `game/assets/generated/`
      (a file in two packs or in none, other bytes, a `.part` or `.import` shipped, a file of
      10 MiB or more left in `mattini.pck` fail it).
- [ ] No file over 100 MiB (104'857'600 bytes): `tools/export.sh` step 5 still refuses one,
      the data packs included. A Release asset may be up to 2 GB, but the limit stays until
      M5 decides otherwise (SPEC §11, §14).
- [ ] The Linux export starts: `tools/export.sh`'s step 6 runs
      `build/linux/mattini.x86_64 --headless --quit-after 300` and requires nine startup lines
      and no `ERROR` line: one per data pack (two), then the terrain's (columns, rows,
      spacing), the buildings' (their count), the photo's, the surfaces', the trees', the
      roofs' and, from 0.5.0, the shadows' (`mattini <version>: shadows village loaded, 4000 x
      6000 cells at 0.5 m`) (M2-02, M2-05, M3-08, M3-14, v0.5.0-05). The sky block prints no
      line of its own (0.4.0): a refused `sky` block would print an `ERROR` line, so "no
      `ERROR`" is its check.
- [ ] `tools/release_checks.sh` passes on `build/linux`: its last line reads `== release checks:
      all passed`, and its five lines go into the record. They replace the hand checks of
      0.3.1 and 0.4.0 that they script (the script's header says what each finds):
      1. `stars`: `mattini.pck` holds `sky/stars.csv` with `game/sky/stars.csv`'s size and MD5
         (a build without it shows a starless night and no ESA credit; from 0.4.0);
      2. `frame cap`: `--print-fps --quit-after 600` prints `Project FPS: 60`, one line per data
         pack and the startup lines, no `ERROR` line (the owner's "4b"; it does not prove the
         15 fps pause cap, which the pause screen's own test does);
      3. `override.cfg`: one beside the executable (a marker version, MSAA off) shows the
         marker in the startup lines, and is removed again (the owner's "4b": MSAA can be
         switched off without a rollback; the Release notes tell the player this route);
      4. `missing pack`: with `mattini-photo.pck` moved aside, DataPacks' `ERROR` line names
         it, "the aerial photo" and the folder, and PhotoGrid's ends "download the release
         folder again"; the pack goes back unchanged (FB-005). The error panel's text is not
         seen here (the release template ignores `--script`): the owner's;
      5. `live log`: started with no `--quit-after`, the output and `user://logs/godot.log`
         hold every startup line while the process runs; then it is stopped by its PID (FB-006).

**The dry run on GitHub** (after the bump is on `main`):
- [ ] `release.yml` dispatched (`workflow_dispatch` runs only the workflow file on the default
      branch; the session's GitHub tools can dispatch it, but cannot create a Release or upload an
      asset: docs/history/blocked/2026-10-29-2.md) with `sha` the 40-hex `main` commit that holds
      the bump, `version` `game/project.godot`'s, `manifest_bytes` and `manifest_sha256` the
      plan's pair, and `dry_run` true (the default). The run is green: the inputs checked, the
      checkout equal to `sha`, Godot and uv from `tools/pins.sh`, the pipeline in the order
      above, the manifest pair, the first import, `tools/export.sh`, `tools/release_checks.sh`
      (`== release checks: all passed`), `tools/release_pack.sh`; the two archives,
      `SHA256SUMS` and the notes kept as the run's artifact for three days.
- [ ] The record names the run (its id, its time, each step that ran long) and copies
      `SHA256SUMS` from its log: the two archives and the ten files inside them. Measured on
      0.4.0's tree (run 41013012718, 2026-10-30): 7 min 35 s on `ubuntu-24.04`, the runner's
      manifest equal to design's pair (`f68275a1…`, the surfaces PNG's zlib included).

**The real run and the draft:**
- [ ] The same inputs with `dry_run` false. The workflow builds again and creates the draft
      Release `v<version>` (target `sha`, title `mattini <version>`): the notes rendered from
      `tools/release_notes.md`, and three assets, `mattini-<version>-windows.zip`,
      `mattini-<version>-linux.tar.gz` and `SHA256SUMS`. It never publishes it and never marks
      it latest.
- [ ] The draft audited before the owner hears of it: its three asset names and sizes, and
      each archive's SHA-256 against its line in `SHA256SUMS` as this run's log printed it; the
      notes name the version, the source sha, every credit the pause screen shows (§A) and the
      rollback that exists (§E). The record carries the draft's URL and the audit's result. The
      session reads the draft through its GitHub tools (`get_release_by_tag`: names, sizes and,
      where GitHub gives one, each asset's `digest`); a container cannot download a Release asset
      (brain.md H6), so where no digest is given the audit is names and sizes against the log's
      `SHA256SUMS` and the record says so.
- [ ] Each archive holds the five files that belong together: the game, `mattini.pck`, the two
      data packs and Terrain3D's library (`tools/release_pack.sh`; their names never change per
      version: an executable finds its `.pck` by its own name, its data packs by the pattern
      `mattini-*.pck` beside it, and Terrain3D's library has a fixed one; M1 close, D15).
- [ ] The owner publishes the draft (their click, on GitHub). The session never does.

## D. The record

- [ ] `docs/releases/v<version>.md` committed BEFORE the chat message: version, source sha,
      the FB ids it closes, what the review found, what this release does NOT prove (the
      visual checks for the owner), *Questions for you* with the defaults taken, and what
      to do if it will not start. Its numbers, beside the previous release's: the allowance at
      go and at publish, the API-equivalent cost of every session, wall clock, commits, code and
      test lines and tests added, and which model ran where (WORKFLOW §Models).
- [ ] Report-back in chat as a copy of the record; owner-reported items separate from
      review-found ones; plain text.
- [ ] The board updated (shipped line, OPEN list, DEFERRED list, the residue); the inbox
      drained (shipped entries to `ARCHIVE.md` with their disposition); `brain.md`'s header
      current; the plan's `Status: DONE (<version>)`.
- [ ] No Routine left running; nothing scheduled after the session. The owner archives the
      session after reading the report-back.

## E. When the owner reports a broken build

Point at the rollback immediately, in the first reply, before any diagnosis: the previous
version's Release, as the Release notes' rollback line names it. For 0.5.0, the first version
delivered as a Release, it is the `dist` branch's folder `mattini-0.3.1/`
(https://github.com/Treak23/mattini/tree/dist/mattini-0.3.1): 0.4.0 was never delivered. Each
later release rewrites that line in `tools/release_notes.md` so that it names the Release before
it: the session decides the words, a builder writes them (`tools/` is production code, DESIGN.md
§Identity). Then diagnose.
