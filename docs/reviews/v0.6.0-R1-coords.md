## What could make the release gate's bytes differ from the rehearsal's

**The new far files and the surroundings block cannot differ silently.** The surroundings block's bytes are a pure function of committed config: `config/surroundings.json`, `config/datasets.json`, `config/world.json`. This is proven by the 2036-byte recomputation above. The steps refuse, before writing anything, unless the heights SHA-256, the pixels SHA-256, the filled fraction and the JPEG SHA-256 equal the committed values. So a difference in the machine, the codecs or the data becomes a loud refusal that names the decoder or encoder, never a different manifest.

The ways the release run can deviate are therefore all refusals or failed jobs:
1. swisstopo republishes a tile or an item. This is refused by name and checksum at `download`, or by the lock's fit.
2. The runner's libs differ. The sources are the `uv.lock` wheels (Pillow's libjpeg-turbo, GDAL's JPEG decode in the rasterio wheel) and Python 3.13.14 from uv 0.11.32. The far files use no Python `zlib`. The surfaces and shadows PNGs do, and they are already guarded by `expected_png_sha256`, which refuses and names the machine's zlib. The rehearsal ran in a container that sets no Python pin, so zlib agreement between that container and the runner is the only environmental difference with an effect on existing blocks. H27 measured zlib 1.3 and 1.3.2 to write the same bytes.
3. K3: a connection reset in a STAC read fails the job.

**The eight old blocks.** The other eight blocks of the 328'184-byte manifest are unchanged code from 0.5.0. Their determinism is established by 0.5.0's runner run, not by this review. I did not verify `a5a3ef65...` itself.

**Thread order.** `_in_parallel` cannot change output. Results are written by index. The raised refusal is the lowest failing index, because the pool runs FIFO and a call is skipped only when an earlier item has failed. Lock and provenance are written with sorted keys, in cell order.

**Provenance order.** The provenance `absent` list is in cell order (east outer, north inner). The lock's is `sorted()` text. They are equal only while ids are fixed-width four digits (true for E 2603 to 2644, N 1075 to 1117). `_check_far_provenance` compares the two lists exactly. This is a latent, not a current, hazard.

## What the review does NOT prove

- Nothing rendered, nothing ran. All Godot behaviour (the camera clamp, the draw, mesh winding, startup time on the owner's PC) is read from code.
- The K1 premise that `Terrain3D get_height` is NaN outside the grid and on holes rests on `test_terrain_loader.gd:104,115` and `test_terrain_loader_nw.gd:121,132`, which assert it. I did not run them.
- That the expected heights, pixels and JPEG are the right values for the real tiles. I did not download the 380 MB of inputs or run the steps. I only checked that the stored values are consistent with the committed lock, world and datasets, and with each other.
- That `a5a3ef65...` is the true SHA-256 of the real manifest. Only its size is reproduced.
- That GDAL's JPEG-in-TIFF decode and Pillow's JPEG encode give the same bytes on the GitHub runner as in the container. They are the same wheels under `--frozen`. The pixel and JPEG gates would refuse loudly otherwise.
- That the real 841 x 861 mesh's startup cost is acceptable. Design measured 1.7 to 2.8 s for the mesh. The reader and loader timing (2.33 to 3.40 s) was taken on a synthetic grid, not the real data, and no gate times it.
- The gate's other lenses (shadows, render numbers, export, workflow prose).
