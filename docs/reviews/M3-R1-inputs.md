### M3-R1-I-01 · P2 · The surfaces PNG's SHA-256 depends on the zlib build, is stored in the description, and so makes `manifest.json` (and design's `3ca0445c…`) a property of the machine's zlib

- **Where:** pipeline/mattini/surfaces.py:578 (`zlib.compress(scanlines, 9)`), :690 (`"sha256": hashlib.sha256(png)` in the description), :908 (`png_sha256 != block["sha256"]`, in `built_surfaces_block`); the description is copied verbatim into manifest.json (manifest.py:202-205); pipeline/tests/test_surfaces_fixture.py:150 (the one place the difference is allowed); docs/SPEC.md:645 and docs/RELEASE.md:40 (the PNG "depends on zlib", "checked for integrity only"); docs/ROADMAP.md FB-002 line ("the same base world on every machine (true already: Hard Rule 5, every file checked by SHA-256)").
- **Claim:** The plan accepts that the PNG is content-identical, not byte-identical, across machines (M3-plan §review plan). But the PNG's own SHA-256 is written into `surfaces/<area>.json`, and `manifest` copies that description into `manifest.json`, so the manifest, which must be byte-identical (Hard Rule 5; the arc plan checks it as `3ca0445c…`, 324'359 bytes), is identical only on a machine whose zlib writes the same level-9 stream as this container's. Nothing refuses on another machine: `surfaces` prints "the classes have the SHA-256 config/surfaces.json expects" and exits 0, and the gate cannot see it, because its one fixture test allows exactly this difference (`assert written == {**block, "sha256": _sha(png)}, "only the PNG's own SHA-256 may differ"`) and no test re-encodes the real grid.
- **Proof:** zlib-ng 2.2.5 stands for "another deflate" (PyPI `zlib-ng` 1.0.0 in a scratch venv; a `sitecustomize.py` on `PYTHONPATH` sets `zlib.compress` to `zlib_ng.compress`; mattini's code is untouched). This container's Python 3.13.16 has zlib 1.3.
  - The real class grid's scanlines (150'015'000 bytes) at level 9: zlib 1.3 gives 1'148'848 bytes (the stream inside A's PNG, byte for byte); zlib-ng gives 950'236 bytes.
  - `PYTHONPATH=zngsite python -m mattini surfaces --raw A/data/raw --out zngout` (clone at `410dbba`): exit 0, prints `the classes have the SHA-256 config/surfaces.json expects, 93d78ba6d89eea27d0ec897d9f5fca244633336ff29378cd2b2fc9def77e5093`. `surfaces/village.png` is 950'293 bytes, SHA-256 `6c045a83…` (A's: 1'148'917 bytes, `8922edf9…`); `surfaces/village.json` differs from A's in one line, `"sha256"`.
  - A's other 23 outputs plus that `surfaces/` folder, then `python -m mattini manifest --out <that folder>`: exit 0, 324'359 bytes, SHA-256 `597926edbc04adde6f657e7702694897241ff80f374d62eef4229c2263459ddd`, not `3ca0445c9109eec4696d654d1c7536f50220f4db04503fab836412f5b0c01065`.
  - `pytest pipeline/tests -k "surfaces or manifest or png"` under the same `PYTHONPATH`: 616 passed.
- **Harm:** On a machine whose Python links another deflate (a zlib-ng build, any fork that chooses other matches) the owner's pipeline run exits 0, says the output is the expected one, and writes a PNG and a manifest that differ from design's and from every other machine's. The release check "manifest `3ca0445c…`" then fails with no message that names zlib, and FB-002's premise (same bytes on every machine) is false for the PNG and the manifest. RELEASE.md §C does not list a manifest comparison at all (the arc plan's close does), so the dependence is invisible to the release walk. The game is not harmed: the description and the PNG on that machine agree.
- **Fix:** Make the PNG's bytes a designed value, as the photo's JPEG is: `expected_sha256` in config/surfaces.json for the village and a refusal "this machine's zlib writes other bytes: zlib <ZLIB_RUNTIME_VERSION>" before anything is written (then the manifest is deterministic wherever the step runs). Smaller alternatives: drop the PNG's `sha256` from the description and let the game check the decoded classes against `pixels_sha256`; or write the IDAT with a deflate of mattini's own. Add the manifest comparison to RELEASE.md §C once one of them holds.

### M3-R1-I-02 · P3 · A cut tile or sheet transfer is told from a good one only by the finished file's SHA-256, after one retry, and the refusal does not say a transfer was cut

- **Where:** pipeline/mattini/download.py:781-785 (`urllib_fetch_file`, `shutil.copyfileobj` with no size check), :97 (`ATTEMPTS = 2`), :916-930 (`_fetch_verified`, the message at :927).
- **Claim:** The terrain, buildings, photo and surface downloads send one GET per file, never compare the bytes received with `Content-Length`, and retry once. Python's urllib returns normally from a body cut short (brain.md H9), so a cut is found only after the whole file is hashed, and two cuts in a row end the command with "SHA-256 X does not match the published Y (after 2 attempts)": the words of a republished or damaged file, with no hint that running it again is the remedy. The TLM download measures the size and resumes; the other four do not.
- **Proof:** A local server that answers `Content-Length: 1024000` and sends 512'000 bytes, run through the shipped functions: `urllib_fetch_file` returned normally with 512000 of 1024000 bytes written; `_fetch_verified` ended `DownloadError: tile 2624-1096 of area 'village': <url>: SHA-256 8acfcabd… does not match the published 062af9cc… (after 2 attempts)`. On the real service in this review: `download photo` over a folder with one damaged tile fetched 2624-1096 twice and ended `mattini: error: tile 2624-1096 of area 'village': …: SHA-256 9a24689c… does not match…` with no provenance.json left; the same probe run again fetched twice (first cut, second good) and verified. The wave-1 integration record has the same ending on tile 2624-1097. (My own first download of the four tile datasets, 24 files, had no cut; the TLM's first GET was cut at byte 2'881'152'205 of 2'882'823'552 and its resume finished it: `1 file verified, 2 fetches`.)
- **Harm:** The owner who meets a dropped connection sees a message about swisstopo's checksum and may suspect a republish or a bad file; the fix (run it again) is not named. Nothing wrong is written; the rerun heals.
- **Fix:** In `urllib_fetch_file` compare the bytes written with `Content-Length` when the header is sent and raise `http.client.IncompleteRead` (an HTTPException: the retry loop already catches it, and the message then says "fetch failed: IncompleteRead(512000 bytes read, 512000 more expected)"); add "run the command again" to the exhausted-retries message.
