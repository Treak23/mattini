## Findings

No P0, P1 or P2. Seven P3.

### P3

- **R1-01, seams 03 x M4-10: the process note does not carry what the plan's seam 6 says it
  does.** `docs/briefs/v0.3.1-plan.md:81-84` says M4-10's `test_m4_08_release_hints.gd` and
  `test_main_scene_light.gd` "predate this release; the next release rebuilds them on this
  release's pins (docs/briefs/M4-plan.md's process note)". The note (`docs/briefs/M4-plan.md:14-26`)
  names only M4-06's `fake_tools.py` and `test_m4_06_terrain_look.gd`, and says of M4-10 only
  that its tests of the cap and the packs "stay as regression tests". M4-10's brief copies its
  pins byte-identical (`docs/briefs/M4-10-the-main-scene.md:187, 251, 269`), and its
  `test_m4_08_release_hints.gd` lacks `game/tests/test_m4_08_release_hints.gd:134-137` (true,
  then null: "null after yes gives the question back too"), the lines v0.3.1-03 added to kill
  R11. Measured in my scratch worktree: with those four lines removed and R11 applied
  (`set_exported_for_tests(null)` ignored), the script passes `9/9`, Asserts 65. Downgraded
  from P2 because the whole suite still catches R11 by leakage: the same tree failed 11 more
  tests across six `test_main_scene*.gd` scripts, and my probe saw 55 tests start with the
  export seam on. `test_main_scene_light.gd` is touched by nothing in 0.3.1, so the plan's
  sentence about it does not say why it is listed. Harm: none the owner sees; a killed mutant
  goes back to being caught only by accident. Fix: one bullet in the process note. M4-10's
  `test_m4_08_release_hints.gd` keeps 0.3.1's lines 134-137, and only its `until_m4_10` skip
  goes. Re-word its `fake_tools.py` and `test_export_startup_lines.py` paragraphs onto
  v0.3.1-04. Drop `test_main_scene_light.gd` from seam 6 or say why it is there.
- **R1-02, seam 03 x 05: the executable's folder has two homes.** `data_packs.gd:79`
  (`_init`'s `dir`) and `main.gd:198` each spell
  `OS.get_executable_path().get_base_dir()`. The pins compare main's panel with that
  expression itself (`test_pause_cap_and_pack_panel.gd` `_packs()`), and `_init` is tested by
  nothing (v0.3.1-03 decision 8). If one changes and the other does not (say DataPacks looks for
  its packs in another folder), the gate stays green. Every exported start would then show the
  panel with packs "missing" while the log, which follows `_init`, is clean. Grade: P3, because no
  such change is planned. Fix: one static `DataPacks` function for the folder, used by both
  (`missing_pack_errors(dir)` keeps its pinned signature).
- **R1-03, v0.3.1-01: ripple map b jumps once an hour.** Godot's `TIME` rolls over at
  `rendering/limits/time/time_rollover_secs`, 3600 s by default, and `project.godot` does not
  set it. At the rollover map a's offset moves 3600 x (0.48, 0.64) / 2.0 = (864, 1152) whole
  tiles, which is seamless. Map b's moves 3600 x (0.48, 0.64) / 3.4 = (508.235, 677.647) tiles,
  so its pattern jumps by (0.80 m, 2.20 m) in one frame (computed;
  `terrain_photo.gdshader`, the `ub` line of the water rule). 0.3.0's water jumped too (82.8
  tiles), so this is not a regression. Harm: a one-frame pop of the river's ripples once per hour
  of play, never rendered here. Fix, a later release (the values are pinned):
  `time_rollover_secs=3400` makes both whole (816, 1088; 480, 640), or a b-tile of 3.6 m.
- **R1-04, v0.3.1-01: design-of-record text now stale (Hard Rule 2, docs).**
  `docs/SPEC.md:875` still reads "water darker (albedo x 0.6), smooth (roughness 0.05), with two

  leaves both to the session at the record; listed so the record does not miss them.
- **R1-05, v0.3.1-01's pinned render check: two comments claim what the check does not do.**
  `game/tests/render/render_photo.gd:2` says the check is "of where the photo shader puts the
  photo and the surface classes", but the classes check reads the water class alone. `:64` says
  WATER_TOLERANCE covers "the light's highlight on roughness 0.3 included", but `:117-121` switch
  the highlight off (`light_specular = 0.0`). These are known and accepted (brief v0.3.1-01
  decision 6; the board's residue, round R2 P-03). Fix: the next re-pin of the file.
- **R1-06, v0.3.1-04: the batch review's two notes, confirmed by reading.** (a) The stand-in
  pack tool packs an empty folder (`fake_tools.packed_files` returns no file, `write_pck` writes
  an empty pack), where `game/tools/pack.gd:31-32` refuses "holds no file to pack". So no export
  test can see step 4b refuse an empty packed folder. (b) The check after 4b

  leaves `build/linux` and `build/windows` holding a fresh export without one pack. RELEASE.md
  §C copies only after exit 0, so today there is no harm. Fix: the stand-in refuses an empty
  folder as `pack.gd` does; the refusal could name `build/` as unfinished.
- **R1-07, v0.3.1-02: nothing shows 4x MSAA starting on the village, and the rollback is

  the village. Downgraded: a crash on the owner's GPU cannot be proved here. A one-file fallback
  exists. With `game/override.cfg` set to `[rendering]` /
  `anti_aliasing/quality/msaa_3d=0`, my probe read the root viewport's `msaa_3d` 2 without it
  and 0 with it (editor binary, project folder). Godot documents the same file beside an exported
  executable, which I did not run (no template here). Fix: the record's look list and the dist
  README tell the owner this file before "roll back to 0.3.0".

## What this review does NOT prove

- That anything renders or looks right on the owner's PC: the river's colour, ripples, drift
  and bank; smoother edges under MSAA; whether 4x MSAA starts on the real village on any GPU.
  The release gate's start is headless and never draws.
- That an exported build logs DataPacks' line and PhotoGrid's release hint, or shows the error
  panel. Every run here used the editor binary through `ReleaseBuild`'s test seam, and the
  release template ignores `--script`. RELEASE.md §C's run with the photo pack moved aside is
  that proof; the panel stays the owner's to see.
- That a release export flushes its log while it runs. The editor binary flushes anyway (the
  `.debug` key); §C's run is that proof.
- That `tools/export.sh`'s step 2b and the check after 4b behave on the real village. Only the
  stand-ins ran: no `data/` and no export template here.
- The GPU load, heat or fan noise at 60 and at 15 fps. Only that the engine sleeps, headless:
  17.9, 66.0 and 16.7 ms a frame.
- The cost on a GPU of `water_weight`'s 36 class reads per terrain fragment.
- The Windows build.
- That the pins are the right tests, or that no other mutant survives. I ran two mutants of my
  own (the typed constant; R11 with M4-10's seam test), not the batches' rows again.
- The next release's cut: M4-10's pins use classes 0.3.1 does not have and were only diffed,
