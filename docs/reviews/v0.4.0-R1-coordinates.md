## (b) The sun, the moon, the stars

- Convergence sign, from first principles: Zermatt is east of the LV95 central meridian, so meridians lean west going
  north, true north lies at grid azimuth -0.226, grid azimuth = true azimuth + true_to_grid_deg(-0.2258). The code adds
  it (`sun.x + _site.true_to_grid_deg`), and the rig's frame has north = `_bearing(true_to_grid)`, east = `_bearing(true_to_grid + 90)`:
  consistent with each other and with the sun.
- Stored values vs swisstopo's approximate formulas at the box centre (2624000, 1096500): lat 46.0196196 vs stored
  46.0196233, lon 7.7485330 vs 7.7485397, convergence 0.22615 vs 0.2258 (inside the test's 1e-4 and 0.01 bands). The two
  fixture sky configs agree with the same formulas too (0.4851 vs 0.4849; 0.1933 vs 0.1929).
- Start moment: a Python port of `SkyClock.sun` at 1694000400 (2023-09-06T11:40Z), 46.0196233 N, 7.7485397 E gives true
  azimuth 184.8759, elevation 50.3355, grid 184.6501. Spec 184.65 +/- 0.05 and 50.34 +/- 0.05 hold. The GUT test
  (`test_main_scene_light.gd`) reads them from the main scene's Sun light through the fixture world, plus an exact
  comparison with SkyClock, a turned world (x=+n, z=+e) and a +5 deg convergence, so a hard-coded axis or a sign flip fails.
  `CompleteWorld.SKY` is tied to config/sky.json by a test (line ~249).
- Celestial basis, derived by hand: Q = U cos(phi) - N sin(phi), X0 = Q cos(theta) - E sin(theta), Y0 = Q sin(theta) + E cos(theta),
  pole P: equal to `_celestial_basis`. u = RA/360, v = (90 - dec)/180 equals the star image's mapping. The mat3 transpose
  convention is "measured in software Forward+" by the pin author; I did not re-measure it.
- Hard-coded origin or axes: grep of the added lines in game, pipeline, tools, config for 262xxxx, 109xxxx, "+e", "-n": none in
  production code (the hits are the test fixture world 2700000/1200000 in tests and one Basis in a test helper).
- 32-bit: `time_unix` is a 64-bit float; the sun and moon come back as Vector2/Vector3 (32-bit), azimuth quantised to about
  1.5e-5 deg (the known 360.0 case aside). No LV95 coordinate is subtracted in 32-bit anywhere new.
- Stars: the table is ICRS (J2000 axes), the sidereal angle is of date, so the stars sit about 0.33 deg (precession since J2000
  to 2023.7) away from the sun's and moon's frame. Documented in sky_rig.gd and the test header ("0.13 to 0.35 deg").

## (c) Determinism

- Flow: only floating-point operation is `atan2`/`degrees`/`/1.5`/`round` per segment; a boundary hit needs the bearing
  within about 1e-13 deg of (k+0.5)*1.5, which has no integer-mm vector to produce it in practice; the expected SHA-256s refuse a
  machine that differs (checked before any write). PNG bytes depend on zlib, refused by `expected_flow_png_sha256`, as the classes.
- Sky block: `json.dumps(indent=2, sort_keys=True, ensure_ascii=False) + "\n"`, `.part` rename, no time, host, locale or absolute
  path in the file (the progress line with the path goes to stderr). I recomputed the committed shadows fixture's
  `sky/fixture.json`: SHA-256 4d010fc9... equals the one the test pins.
- stars.csv: stdlib only, input size and SHA refused first, `.4f`/`.2f` formatting, sort on written values, LF. Spot values
  (Sirius, Arcturus, Vega) match the known J2000 positions. 5048 lines = 4 header lines + 5044 stars, 112045 bytes, SHA e2a98eea... as pinned.
- Manifest 324931 bytes: from 0.3.1's 324359 (RELEASE.md) plus the flow object (349 bytes: nine lines, keys sorted, `"cell_m": 2.0`) plus
  the sky block (223 bytes with its comma, between `schema` and `surfaces` in sorted order) is exactly 324931. The SHA-256
  a03c5722... I could not check without the 0.3.1 file (unverified); the byte arithmetic agrees with the plan.
